1. Summary and recommendation

JobAgent has two runtime parts: a Next.js 16 frontend on Vercel, and a FastAPI backend (backend/) that holds all business logic: AI matching, Smart Apply, Proof of Fit, billing webhooks, email and a daily background sync. Data, sign-in and file storage live in Supabase (managed Postgres, Auth and Storage).

The backend is already packaged as a Docker image and is stateless apart from a few in-memory guards, which makes it a straightforward fit for Amazon ECS on Fargate.

Recommendation. Move the backend and its daily job to AWS (ECS Fargate behind an Application Load Balancer, scheduled by EventBridge). Keep the frontend on Vercel and the database on Supabase for now. Moving those adds weeks of work and risk for no user-visible gain at the current scale. 2. Current architecture

The browser talks to three places: Vercel for pages, the FastAPI backend for every /api/... call (authenticated with the user's Supabase access token), and Supabase directly for sign-in and a few owner-scoped reads protected by row-level security. The only server route left in Next.js is the Google OAuth callback, because it must set session cookies.

3. Data model and security model

The schema is supabase/schema.sql plus migrations 002–013, all idempotent. Every table has row-level security; the backend uses the service-role key, which bypasses it, so every backend query filters by the authenticated user's id explicitly.

TableHoldsBrowser access
profilesOne per user: contact, parsed resume, targets, plan, account type, talent-pool opt-inOwn row (billing columns guarded by trigger)

matchesPer user × job: score, reason, skills, status, tailored resume, cover letter, interview prepOwn rows
usage_eventsCredit ledger and token metering (hosted vs BYOK)None; functions callable by service role only
user_ai_keysUsers' own AI keys, Fernet-encryptedNone (deliberately no policies)

Security controls already in the code

  • Auth: every API call carries the Supabase access token; the backend verifies it with Supabase Auth (30-second cache).
  • Admin: requires both an allow-listed email and profiles.is_admin.
  • Webhooks: HMAC-SHA256 signatures, constant-time comparison, idempotent by event id.
  • Cron: /api/cron/sync refuses every call unless CRON_SECRET matches.
  • BYOK keys: encrypted at rest with rotating Fernet keys; never returned to the browser; fixed provider base URLs.
  • CORS: only the app origin (plus configured previews); no cookies.
  • Privacy: recruiters get contact details only after the candidate accepts an introduction.
  • Errors: internal details stay in logs; Sentry sends no request bodies or IPs.
Constraint that shapes the AWS design: rate limits, the per-user match lock, the per-proof answer lock and the "sync already running" guard live in process memory. They are correct for one backend process. The AWS service therefore runs one task; section 12 lists what changes before running more.

4. Key request flows

Find jobs

  1. POST /api/jobs/fetch pulls Adzuna and company boards for the user's roles and country into the shared pool.
  2. The browser loops POST /api/match; each call ranks unscored jobs by keyword overlap, then AI-scores up to 24 (4 at a time).
  3. Scores are saved to matches; the loop ends when remaining is 0 or the plan cap is hit.

Smart Apply

  1. Consent modal, then POST /api/apply/smart.
  2. Credits are reserved atomically (consume_credits) unless the user's own key is used.
  3. Two quality-model calls: tailored resume (with ATS score) and cover letter. Credits are refunded if either fails.

Proof of Fit

  1. POST /api/proofs writes 3 role-specific questions (our key, monthly cap).
  2. Each answer is timed by the server; a follow-up is generated from it.
  3. After 6 answers, grading scores skills with verified quotes; an invited proof starts the recruiter's decision clock.

Payments and daily sync

  1. Checkout is created by the API; Razorpay or Lemon Squeezy calls the signed webhook, which updates the plan once per event.
  2. Daily at 06:00 UTC: expire overdue recruiter decisions, refresh the job pool, match active users, send digests and 7-day follow-ups.

Timing note for the load balancer: the longest synchronous calls (Smart Apply, proof grading) take tens of seconds, so the ALB idle timeout is raised to 120 s (section 5).

7. Security on AWS

Accounts and people

  • Root user: hardware or app MFA, no access keys, used only for billing.
  • People sign in through IAM Identity Center with MFA; no long-lived IAM user keys.
  • CloudTrail on in all regions; AWS Budgets alert at 80% and 100% of the monthly budget.
  • Optional: separate staging and prod accounts under AWS Organizations.

Network

  • alb-sg: inbound 80/443 from anywhere.
  • api-sg: inbound 8000 only from alb-sg. Required because uvicorn trusts forwarded headers (--forwarded-allow-ips='*').
  • sync-sg: no inbound. Outbound 443 for both tasks.

IAM roles (least privilege)

  • Task execution role: pull from ECR, write its log groups, read /jobagent/prod/* parameters and decrypt with their KMS key.
  • Task role: none needed today (the app calls no AWS APIs). Keep it empty.
  • Scheduler role: ecs:RunTask on the sync task definition and iam:PassRole for its two roles.
  • GitHub deploy role: assumed through OIDC, restricted to this repository's main branch; push to the one ECR repository, register task definitions, update the one service.

Data in transit

  • TLS at the ALB; all outbound calls (Supabase, AI, payments) are HTTPS.
  • Phase 3: AWS WAF on the ALB with AWS managed rules and a per-IP rate rule.

8. CI/CD pipeline

  • Rollback: automatic if the new task fails health checks (deployment circuit breaker). Manual: aws ecs update-service --task-definition jobagent-api:<previous>, which takes about two minutes.
  • Database changes: migrations are idempotent and additive; apply them in the Supabase SQL editor (staging first), then deploy. Never deploy code that needs a migration before the migration has run.
  • Staging: a second service (jobagent-api-staging, its own SSM path and Supabase project) deployed from the version2/feature branches. Optional for launch, recommended before onboarding colleges.

10. Deployment plan and cutover

Infrastructure should be written as code (Terraform or AWS CDK) and kept in the repository under infra/, so production can be rebuilt and reviewed. The steps below are the order of work either way.

Phase 0 · half a day · prerequisites

Account and inputs

  • Create the AWS account; root MFA; IAM Identity Center admin user; enable CloudTrail; Budgets alert (e.g. $100).
  • Confirm the Supabase project's region; if it isn't Mumbai, note the added latency (section 13).
  • Decide DNS: move the zone to Route 53, or delegate only api.getjobagents.xyz.
  • Collect every backend secret (appendix) from the current .env / dashboards.
Phase 1 · 1–1.5 days · build

Infrastructure as code

  • VPC, subnets, internet gateway, security groups.
  • ECR repository; push a first image by hand to prove the build.
  • SSM parameters under /jobagent/prod/.
  • ECS cluster, both task definitions, IAM roles, log groups.
  • ACM certificate (DNS validation), ALB, target group, listeners, Route 53 alias.
  • API service (desired count 1) with circuit breaker; confirm https://api.getjobagents.xyz/health returns {"status":"ok"}.
  • EventBridge schedule created disabled (enabled at cutover so two schedulers never run together).
  • GitHub OIDC provider and deploy role; deploy-api.yml workflow; first deploy through the pipeline.
  • CloudWatch alarms and SNS email subscription (confirm the subscription email).
Phase 2 · half a day · cutover (low-traffic hour, IST night)

Switch traffic

  1. Apply migrations 009–013 in Supabase (staging first) if not yet applied.
  2. Smoke test against the AWS URL with a test account: sign in, upload resume, Find jobs, Smart Apply, start and finish a Proof of Fit, recruiter invite and decision, admin page.
  3. Vercel: set NEXT_PUBLIC_API_URL=https://api.getjobagents.xyz; set CORS_ORIGINS in SSM for preview URLs if used; redeploy the frontend.
  4. Razorpay and Lemon Squeezy dashboards: webhook URLs to https://api.getjobagents.xyz/api/webhooks/razorpay and /lemonsqueezy; send a test event from each.
  5. Disable any other scheduler (Render cron, GitHub cron), then enable the EventBridge schedule. Run the sync task once by hand and read its log.
  6. Watch alarms, Sentry and logs for 24 hours. Keep the previous host running but idle for one week, then delete it.
Phase 3 · 1 day · hardening

After launch

  • AWS WAF on the ALB: AWS managed common rule set + per-IP rate limit.
  • Staging environment and a written runbook (deploy, rollback, rotate a secret, restore Supabase backup).
  • Supabase: confirm daily backups / point-in-time recovery on the paid plan; test a restore into staging.
  • Rotate any secret that was ever pasted into chat, email or a shared document.
Rollback at cutover: repoint NEXT_PUBLIC_API_URL and the webhooks back to the previous host and redeploy Vercel. Both hosts use the same Supabase database, so no data moves in either direction.

12. Scaling roadmap

SignalAction
CPU or memory alarms, or p95 latency rising with trafficScale up the one task: 1 vCPU / 2 GB, then 2 vCPU / 4 GB. No code changes.
Need more than one API task (availability or load)Move rate limits and the per-user / per-proof locks to a shared store (ElastiCache Serverless for Redis/Valkey, or Postgres advisory locks); then set desired count 2+ with target-tracking autoscaling.
Daily sync exceeds its 25-minute budgetSplit by user batches into several scheduled tasks, or move matching to an SQS queue with a worker service.
Long AI calls hold connections (Smart Apply, grading)Make them asynchronous: enqueue to SQS, worker writes result, browser polls (the matching loop already works this way).
Groq rate limits at placement-season peaksSet the hosted fallback provider; raise HOSTED_MAX_CONCURRENCY only with a higher Groq tier.
Compliance or enterprise/college contracts need data in AWSPrivate subnets + NAT; consider RDS for Postgres with logical replication from Supabase as a first step; keep Supabase Auth until a Cognito migration is planned.
